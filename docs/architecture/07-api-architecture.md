# 07 — API architecture

## 1. Shape (KEEP)

- **Internal API: tRPC v11.** One `appRouter`, called in-process by the web app and over
  HTTP at `/api/trpc` by native clients later. End-to-end types; Zod on every input; Arabic
  error copy mapped from stable domain codes.
- **External-facing REST: route handlers** for anything that is not a first-party client:
  `/api/webhooks/{provider}` (Paymob, Bosta, SMS delivery receipts) and `/api/jobs/{name}`
  (cron triggers). Zod-validated bodies, HMAC-verified, idempotent.
- No GraphQL, no public REST API for third parties before Phase 2.

## 2. Resource boundaries and naming (current routers, kept; additions marked +)

| Namespace | Audience | Procedures |

| `catalogue` | public | `productBySlug`, `productsByHouse`, `houseBySlug`, `directory`, + `list` (home grid), + `search` (moves from `core/catalogue.ts`), + `compare` |
| `cart` | public | `price` |
| `orders` | public | `place` (+ idempotency key), `byReference`, + `cancel` (reference + verified phone, pre-dispatch) |
| `reviews`, `returns`, `support` | public/aftercare + seller + platform | as today; `reviews.submit` requires verified phone |
| `applications` | public intake + platform | as today |
| `seller` | house staff | `queue`, `confirm`, `decline`, `dispatch`, `payouts`, `statement`, + `ledger`, + `performance` (doc 06 §11 indicators), + `staff.*`, + `profile.*` |
| `listings`, `photos` | house staff | as today |
| `platform` | operators | `workQueue`, `markDelivered`, + `markRefused`, + `cancel`, `recordRemittance`, + `payouts.draft/approve/markPaid/hold`, + `refunds.*`, + `houses.suspend` |
| `admin` (+) | admin role | `commission.rules.*`, `feeTerms.*`, `policies.*`, `staff.*`, `privacy.*` |
| `content`, `contentImages`, `site`, `audit`, `insights`, `analytics` | as today | |

Naming: `namespace.verbNoun` for mutations, `namespace.noun` for queries; ids are UUIDs;
public lookups use slugs and references. Money crosses the wire as integer piastres, dates
as ISO strings, enums as their stable codes with copy resolved by `@diyar/i18n` on the
client.

## 3. Authentication and authorisation at the boundary

- Web: session cookie read at the composition root (`apiContext`) — never in a router.
- HTTP: `Authorization: Bearer <session id.signature>` resolved by the same composition
  root (one line, as the route comment says). No cookies on `/api/trpc`; no
  `Allow-Credentials` (kept).
- Procedure builders carry the permission, not the role: `sellerProcedure('orders.act')`,
  `platformProcedure('payouts.approve')` — see `05-security-architecture.md` §2.

## 4. Pagination and filtering

- Lists that grow (audit, orders, ledger, tickets, listings) use **keyset pagination**
  (`cursor` = opaque base64 of `(sort key, id)`, `limit` ≤ 100), as `audit.recent` already
  does. Offset pagination is not used.
- Filters are explicit Zod enums/ranges per procedure (as `/search` does); free-text
  search is one `q` field, normalised server-side.
- Sorting is an enum of named orders, never a raw column name.

## 5. Validation and errors (KEEP + extend)

- Zod at every input with Arabic messages; `ZodError → BAD_REQUEST` with field paths.
- Domain errors carry stable codes; `errors.ts` maps to tRPC codes. Add codes for
  `STOCK_UNAVAILABLE`, `IDEMPOTENT_REPLAY`, `PERMISSION_DENIED(permission)`,
  `PAYMENT_DECLINED`, `SLA_LOCKED`.
- Error shape to clients: `{ code, message(ar), field?, retryAfter? }`. Never a stack.
- Unknown errors → Sentry with request id → generic Arabic message carrying the request id
  so support can find it.

## 6. Idempotency

- `orders.place`, `returns.request`, `support.open`, `applications.submit`,
  `platform.runPayout`, `platform.recordRemittance`, `platform.refund` accept
  `idempotencyKey` (UUID generated by the client per attempt-set). Stored in
  `idempotency_keys(scope, key) → response`, 24 h. A replay returns the stored response;
  a key reused with a different payload is `CONFLICT`.
- Webhooks: `(provider, provider_event_id)` UNIQUE; duplicate → 200 with no work.
- Jobs: `job_runs(job, run_key)` UNIQUE; a re-trigger of the same run is a no-op.

## 7. Versioning

- tRPC is consumed only by first-party clients built from the same repo; the web app is
  always in step. For native apps: additive changes only; a breaking change ships as a new
  procedure (`orders.placeV2`) and the old one is removed after the minimum supported app
  version passes it. `x-diyar-client` header carries app version; the server can refuse
  below a floor with a specific error the app renders as "update required".
- Webhook routes are versioned in the path when a provider changes payloads
  (`/api/webhooks/paymob/v1`).

## 8. Rate limiting

Per procedure rule (as today), keyed on phone / house / IP, backed by the database table
(DEBT #2), with edge limits at Cloudflare. `TOO_MANY_REQUESTS` carries `retryAfter`.

## 9. Documentation

tRPC types are the contract. Add a generated procedure catalogue (name, auth, input schema
summary) produced by a script into `docs/architecture/api-catalogue.md` on each release, so
the business founder can read what exists without the code.
